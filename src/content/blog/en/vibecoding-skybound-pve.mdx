[Skybound PvE](/en/projects/skybound-pve) grew out of a multiplayer flight prototype I built with Gemini. The prototype had rooms, accounts, a shrinking play area, and real-time updates through Supabase. When I picked it up again, I wanted a game I could open in the browser and start playing right away.

## Decide what the first run needs

I settled on a single-player loop: take off, fight waves of enemies, and try to beat your score. I kept the 3D scene and the flight controls. I dropped the lobby, login, and shrinking zone from the new game. Scores could live in the browser while I tested whether the loop was fun.

That gave Codex a first slice of work with an end I could check. I wanted to go from the start screen to flight, face an enemy, finish a run, and see the score.

## Write down the decisions before handing over the code

I used a planning skill to work through questions with Codex before implementing the new loop. Could I defer global rankings? Did an enemy need everything the player's aircraft used? Which code was still written around a remote player?

I put terms like *run* and *wave* in the project context and logged larger decisions in short architecture decision records. The choice to store scores locally was one of those records. It gave later work a clear starting point when a leaderboard came up again.

## Check the result in the browser

After the first loop was playable, I used Codex to review where the code still assumed a multiplayer match. A computer-controlled enemy and a remote player have different responsibilities. Keeping them separate made it easier to work on waves without bringing the room logic back into the game.

Gemini helped build the flight prototype. Codex helped give it a smaller scope that I could check by playing a run. [Play Skybound PvE](https://planes-pve.vercel.app/).
